# 却下済み提案（rejected proposals）

「〇〇はやらない／採用しなかった」という設計上の却下判断だけを記録する。
却下理由を残しておかないと、同じ提案が後から何度も持ち上がり、毎回同じ議論をやり直すことになる。

- 記録対象は**却下した案のみ**。採用済みの設計はコードと AGENTS.md（「アーキテクチャ上の設計判断と既知の制約」など）が正本であり、ここには書かない
- 過去の議論の結論として却下が確定した時点で追記する。検討中のものは書かない
- 却下の根拠が後から覆った（環境・前提が変わった）場合は、該当エントリを削除せず取り消し線で無効化し、無効化した根拠を残す

## エントリの形式

各エントリは次の3項目で書く。

- **却下した案**: 提案された内容を一文で
- **却下理由**: なぜ採用しないのか。測定値・設計上の制約など、検証可能な根拠を添える
- **この判断が無効になる条件**: どんな前提変化があれば再検討に値するか

## 既存の却下系記述

以下は却下済みの判断が本文書ではなく各文書に直接記録されているもの。重複してここへ移さず、参照だけを示す。

- 録画フォルダスキャンで「起動時に全パスを先に収集・ソートしてから処理する」構造を採用しない判断 → `AGENTS.md` の「録画フォルダスキャン (RecordedScanTask) の設計判断」
- upstream 由来で差分がほぼゼロの巨大ファイルを行数だけを理由に分割しない方針 → `AGENTS-BS4K.md` の「巨大ファイルと例外処理の方針」
- DB に MySQL / PostgreSQL を採用せず SQLite とした判断 → `AGENTS.md` の「技術スタック」
- HTTP 直接アクセスを受け付けず loopback のみでリッスンする構成の理由 → `AGENTS.md` の「HTTPS が必須な理由」
